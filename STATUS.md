- Each Business browser keeps one durable HttpOnly cookie containing only a stable opaque BFF session handle newly generated at login and stored hashed in BFF. The Business server SDK—not browser JavaScript—uses it server-to-server to obtain one BFF-signed ten-minute JWT for the requesting tab's current context. Ordinary renewal changes only that tab's JWT, so concurrent tabs, lost responses and logout do not race to replace the shared cookie. Logout, expiry or revocation invalidates the central session row. Before membership the JWT is onboarding-scoped; afterward it is bound to one validated active account and can be verified by both the Business backend and allowed shared BFF APIs. This replaces the earlier two-short-JWT model and preserves independent account contexts across tabs.
- Every login attempt is browser-transaction-bound by SDK-managed protected random state, an S256 PKCE verifier retained only in a short-lived HttpOnly transaction cookie, a provider nonce and BFF binding to the exact Business environment and registered callback. Concurrent attempts have independent cookies; the one-minute handoff code is atomically single-use, and any swapped or replayed state/code/verifier/nonce/environment/callback is denied. Businesses configure none of this.
- BFF is authoritative for the generic, Business-environment-scoped account system: accounts, memberships, fixed roles and account-policy configuration in Build 2, then registered plans and effective shared entitlements when Build 4 has their first real paid caller. Each Business chooses those policies through validated configuration/CLI but does not reimplement or separately store the shared machinery; it owns only its product-specific records and their user/account data scope. BFF therefore validates account context itself before signing the shared JWT rather than trusting account claims from a Business backend. There is no lasting accountless mode. Login creates the environment-local user and secure session but no temporary account; without a membership the user is `onboarding_required`, receives an onboarding-scoped JWT and may access only onboarding/recovery/sign-out. Two independent Business settings decide whether first sign-in creates an account on the default account policy and whether ordinary users may create accounts; all four combinations are valid and invitations remain separate. The shared model has no structural personal/team/organization account kinds: one account may later change plans and gain paid features while retaining its ID and data. Ownership is a subset of the total per-user membership limit. Build 2 implements its active account/membership path, roles, invitations and ownership transfer; Build 4 adds plan/subscription tables, product/seat entitlements, restrictions and downgrade enforcement.
- Accounts always own subscription entitlements, but product data may be user-scoped, account-scoped or mixed according to Business code and schema. The authenticated account context supplies both IDs; entitlement, membership authorization and record ownership remain separate concepts rather than one overloaded “permission” setting.
- The ten-minute BFF-signed current-context JWT is the normal hot-path snapshot for user, session and—after selection—active account, membership and compact fixed permissions. Those values are resolved during issuance/renewal; ordinary Business and BFF APIs verify locally and query only relevant data. Build 4 extends the versioned context with real product/seat entitlements; billing, quotas, seat changes and high-risk state still require authoritative reads.
- Business account/session policy is configured through the repository `configure-business-auth` skill backed by the validated operator CLI. It asks scenario questions one at a time, explains interacting defaults, shows exact JSON and requires a compatible single-use preflight plus explicit confirmation before apply. The backoffice remains read-only and shows bounded environment customer state plus implemented Business-default/account-override policy provenance; no fictitious subscription source is exposed before Build 4.
- `maxAccountMembershipsPerUser` defaults to one, counting both owned and joined accounts. A Business that lets users keep an automatically created account while joining another must explicitly raise the limit; invitation acceptance fails when the user is already at capacity.
- `memberInvitationsEnabled` defaults to false. Build 2 may enable it through the Business default or an explicit account override; Build 4 may also derive it from a registered plan. Creating and accepting an invitation still requires inviter authorization, recipient membership capacity and an available seat.
- `adminRoleEnabled` defaults to false. When enabled, the fixed limited Admin may manage invitations and ordinary Members but cannot manage the Owner, assign/remove other Admins or transfer ownership; custom granular roles are outside the MVP.
- `ownershipTransferEnabled` defaults to false but is a real Build 2 capability. When enabled, transfer requires fresh reauthentication through any currently enabled provider already linked to the same private principal—matching email or an unlinked provider is insufficient—plus explicit confirmation. BFF issues a single-use proof valid for at most five minutes and bound to the current session, account and intended new Owner; the atomic transfer consumes it, preserves exactly one Owner and permanently audits the change. The development dummy provider exercises the same current-Owner proof and wrong-user denial, while production has no dummy trust path.
- Build 2 implements only the active account path; it does not ship unused commercial-restriction machinery. Build 4 adds restrictions with the first real subscription flow. A voluntary downgrade is rejected unless the account already fits the target plan. If expiration or payment failure forces an invalid state, all users, memberships and data remain, ordinary product access is restricted and Owner/Admin remediation access remains until payment or usage is corrected; nobody is removed automatically.
- Membership role, account-wide plan entitlements and optional per-member seat entitlements are separate. Build 2 counts each active membership as one standard unit of `seatLimit` and adds no seat-assignment table; Build 4 adds real plan/seat entitlements when its paid caller needs them. Admin authority does not imply premium product access, and a premium seat never grants administration.

They are not current scope or accepted ADRs; later relevant brainstorms must re-evaluate them before planning.
- `createAccountOnFirstSignIn` defaults to true, creating the default account and Owner membership. Businesses needing organization details, managed provisioning or invitation-first onboarding explicitly disable it and use the restricted `onboarding_required` state until membership exists.
- `userAccountCreationEnabled` defaults to false. Businesses supporting multiple user-created workspaces must explicitly enable it and raise compatible owned-account and total-membership limits.
